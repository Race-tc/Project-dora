4. Safety Acknowledgment

Read this section in full before using the Software. DORA can read from and write to your vehicle's engine control unit. Used incorrectly, it can damage an engine or drivetrain, cause a vehicle to become unsafe or non-compliant to drive, and cause financial loss. By accepting this EULA you confirm you understand and accept the risks below.

4.1 Real ECU flashing risk

Writing a calibration to a real ECU ("flashing") is not a simulated or reversible-by-default action. An interrupted flash, an incompatible map, or a corrupted ROM file can leave an ECU unresponsive or a vehicle inoperable, and may require specialist recovery or replacement hardware to fix. You are responsible for using a stable power supply, a reliable connection, and a verified, vehicle-appropriate ROM file before every flash, and for keeping a backup of the original calibration before writing anything new. DORA's Brick Recovery Mode can attempt a real recovery flash, but only for STM32-based ECU hardware accessed directly via its own programming pins (not the OBD-II connector), and this recovery path has not itself been tested against real silicon by RACE. For any other ECU hardware, or if Brick Recovery Mode doesn't apply, there is no recovery path available through the Software.

4.2 Subaru SSM live tuning

For one protocol only — a vehicle connected live via Subaru SSM in DORA's dedicated live-tuning mode — editing a value on a tuning screen and clicking Apply writes that value directly to your vehicle's live RAM calibration and takes effect immediately on the running engine, without a separate flashing step. This write is temporary (it doesn't survive an ECU power cycle) and only happens once you've confirmed your vehicle's RAM offset in the live-SSM connection dialog. For every other protocol and connection, editing a value on a tuning screen affects only the built-in simulator until you flash it. Where the SSM live-write path applies, you're responsible for the consequences of any value written to the running engine in exactly the same way as for a flashed change.

4.3 Known limitations

Some features are limited in ways you should know about before relying on them for a real vehicle: the CAN Bus Analyser's real-hardware interfaces aren't yet wired up and default to Simulator mode; the J2534 pass-thru driver path is implemented against the published specification but hasn't been exercised against a real J2534 DLL or device; and Remote Tune, which shares a live vehicle's sensor data with a connected guest, has no authentication (anyone able to reach the shared session file can view it), works only when host and guest can access the same file location, and is one-way — the guest can view but not control anything.

4.4 Safety Limits Override

DORA's Safety Guard is enabled by default and is designed to block map writes that fall outside conservative, vehicle-appropriate bounds. It checks values as you edit or apply them in the Software's own tuning screens, and also checks a ROM file's decoded values before ECU Flash or Brick Recovery Mode writes it — but only when a matching XDF/definition has been loaded so the Software can decode that ROM's tables; a ROM flashed with no definition loaded is written without this check. Some panels expose a Safety Limits Override (or equivalent advanced/expert control) that lets you knowingly write values outside those bounds. Using an override is an explicit, manual decision on your part, made outside the tool's own safety checks. You are solely responsible for any consequence of a write made with an override enabled, including but not limited to knock, lean conditions, boost creep, or engine damage.

You are solely responsible for verifying that any change you make keeps the vehicle legal to use on public roads in your jurisdiction, including for MOT/inspection and emissions purposes, before you drive it. Using the Software to defeat emissions controls on a vehicle used on public roads may be a criminal offence in your jurisdiction — that responsibility is entirely yours, not RACE's.
